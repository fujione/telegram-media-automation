# Docker 首次配置设计与验收

此文记录后续首次配置实现约定，未通过下述完整验收前不视为公开发布完成。

## 使用流程

用户下载发布版 Compose，执行 `docker compose up -d`，无需宿主机 Python、uv 或构建工具。默认使用持久化命名卷，固定版本预构建镜像以非 root 用户和只读根文件系统运行。需要复用 NAS 媒体目录时，用户在启动前明确配置挂载及匹配的 UID/GID；启动后检查实际写权限，不递归修改已有目录所有权。

浏览器显示首次配置页。用户在容器终端执行 `mediactl setup-code` 读取一次性初始化码，在 Web 中填写该码、管理员账号密码、自行申请的 Telegram API ID/Hash、可选代理、语言和时区。初始化码不放入 URL、普通服务日志或未认证接口，不复用长期 API Token。

保存后明确提示重启容器以应用 Telegram 配置。重启前后使用同一持久化 API 签名密钥和管理员密码哈希，浏览器会话可继续使用。之后在设置页完成本人 Telegram 验证码/两步验证登录，选择本人可访问的频道，进行搜索、下载、入库及追更。

首次配置过程不在线替换 Telegram gateway；应用重启时只构造一个 gateway 和一组后台 worker，避免多客户端同时操作同一个 Session。

## 状态及安全边界

- 现有部署默认不启用 Web 初始化，已有凭据与 Session 不迁移或覆盖。公开 Compose 显式启用新的首次配置模式。
- 服务首次启动创建持久化签名密钥和独立初始化码，仅容器运行用户可读。未完成配置时 Web/live 可访问，ready 返回未就绪。
- 未认证接口只返回是否需要初始化，不暴露初始化码、Telegram API、代理、路径或管理员身份。
- Web 提交必须验证初始化码，即使请求来自回环地址；失败限速。使用同源校验防止其他站点代发初始化请求。
- 配置先校验并写入同一数据卷下的临时安装目录，设置私有权限并同步磁盘，最终原子发布完整目录。管理员、Telegram 密钥和偏好一起生效；失败保留原配置，重试不覆盖既有安装。
- 初始化完成后入口永久拒绝再次创建账号，初始化码失效；管理员密码重置继续走容器内显式运维命令。
- 秘密不写入镜像、Compose、浏览器本地存储、诊断、备份默认内容或请求日志。错误返回稳定代码和可操作说明，不返回异常原文。

## 验收清单

1. 空命名卷直接启动，容器非 root、根只读；可打开首次配置页，无密钥泄露。
2. 错码、跨源、重复和并发初始化均被保护；故障中断不会留下可用的半套安装。
3. 正确提交后重启，配置和管理员会话保留；初始化码失效，恰好一个 Telegram gateway。
4. 使用独立临时目录验证权限错误及修复指引；不触碰已有媒体目录所有权。
5. 完整覆盖账号登录、频道、搜索、下载、归档、追更、重启、备份及升级。自动化使用受控 Telegram 测试替身验证流程；真实账号步骤单独记录实际结果，不能把替身等同于真实登录或下载。
6. 发布固定镜像与 Compose；仅按公开 README、没有源码开发环境也能完成上述流程。
7. 发布前审计当前文件、所有将公开的 Git 历史、构建上下文、镜像层和发布附件，排除个人部署信息及凭据。
