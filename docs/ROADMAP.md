# 后续工作计划（更新于 2026-10-25）

## 下一轮迭代：上线已有成果，补齐运行可见性

2026-10-26 已部署 0.1.0rc2/schema13，订阅编辑与业务健康诊断已上线；隔离测试、生产任务/订阅指纹、业务就绪及实际重启验证通过。扫描持久化、手动检查与诊断导出的rc3已通过CI及生产数据库副本的NAS隔离迁移/重启验收，尚未更新生产；rc4继续实现Docker首次Web配置与公开部署流程。下一轮按以下顺序实施，不把本地完成等同于用户已经可用。

1. **先上线已有功能**：整理固定版本 Docker 镜像，在隔离容器验证编辑、并发保护、健康原因码与首次安装状态；备份生产数据库并保留旧镜像，再单独更新 TG 服务。验收为 WebUI 可实际编辑订阅、网络故障与未登录明确区分，重启后 Session、任务、订阅和游标保留，兼容回滚不覆盖最新业务数据。
2. **持久化扫描结果**：保存最近尝试、最近成功、最近新增任务、稳定错误码及连续失败信息；扫描历史设置保留上限。页面区分无目标新集、筛选拒绝、频道异常和全局连接故障。验收为重启后仍能解释追更状态，编辑/暂停不被计作资源更新，正常等待不被误报为网络故障。
3. **增加手动检查与诊断入口**：提供“立即检查”和默认脱敏、可预览的诊断导出；扫描中重复点击合并，遵守既有 FloodWait 与退避。验收为不重复入队、不绕过限流，诊断包不含 Session、API Hash、Token、密码、手机号或敏感代理信息。

本轮交付边界是已上线功能和可解释的追更状态。长期没有更新继续提示，由用户判断完结并手动停止追更；不接入外部影视资料或自动完结判断。

## 后续发布迭代：仅 Docker 的公开使用流程

提供固定标签的预构建镜像、Compose 示例和无需宿主机 Python/uv 的首次配置流程；优先完成 Web 引导所需的安全初始化设计。用户使用自己的 Telegram API、账号和频道。用空目录按 README 完整验证初始化、目录权限、登录、搜索、下载、归档、追更、重启及升级，再整理 GitHub 发布材料和版本说明。

完成标准：普通用户只准备 Docker，按公开文档就能独立使用；个人部署信息与凭据不进入公开仓库或镜像。之后再按反馈选择搜索继续加载、Web 质量策略等功能。

本计划依据当前代码、功能覆盖表和验收记录制定。阶段一本地收尾结果见 RELEASE_BASELINE.md；后续阶段是建议优先级，不表示功能已实现，也不表示已批准新的生产部署。

## 阶段二：改善追更日常管理

优先功能为订阅编辑：修改搜索词、季、待补集、下一集、持续追更模式和频道范围，无需删除重建。

2026-10-01：订阅编辑已在本地实现并验证，行为与接口见 SUBSCRIPTION_EDIT.md，当时仅做本地验证。2026-10-25 已通过新 fnos 技能的 OAuth 连接 NAS，后续部署优先复用该授权；SSH 密码不作为该连接方式的前置条件。

实施前明确三类状态的关系：用户计划、扫描游标、已创建任务。编辑不能回退已完成计划、重复入队或静默改写现有任务；频道范围变化需按频道保留可复用游标，并让旧范围候选退出当前选择。使用版本校验处理编辑与扫描并发。

扫描已显示等待集数、拒绝原因、部分频道异常和长期未推进提示。后续按实际需要补充手动“立即检查”；该操作需去重，并遵守现有 FloodWait 与频道退避窗口。

订阅与任务关联优先检查现有数据能否准确表达；若不足，再增加显式关联，不能按剧名猜测。

完成标准：编辑无需重建订阅；扫描期间编辑/暂停不会按旧计划创建任务；重复操作不会产生重复任务；扫描失败可定位到频道且不妨碍其他频道与下载。

## 阶段三：补齐运维与恢复能力

2026-10-25：生产代理故障已恢复并验证重启持久化；健康原因码、实际连接状态和业务健康探针已在本地实现并验证。扫描摘要持久化与诊断导出仍待实施，本次未替换生产应用镜像。

1. 增加持久化的最近扫描摘要或受限历史，保留检查时间、结果和稳定错误类型；设置保留上限，避免数据库持续膨胀。现有 scan_status 仍是内存状态，先明确数据模型再迁移。
2. 演练数据库备份在隔离目录的恢复，核对任务、订阅、游标、归档计划与事件；区分数据库备份、配置/凭据保护和媒体备份。
3. 制定可复用的升级核验流程：当前状态快照、在线备份、兼容性检查、单服务更新、健康与业务连续性验证、兼容回滚。使用固定版本标识，保留断点与 Session。
4. 提供诊断信息导出，默认脱敏且内容可预览；不导出 Token、API Hash、Session、密码、手机号及敏感代理信息。
5. 为替换旧文件备份提供可见清单与空间统计；是否增加显式恢复入口另行设计，保留冲突保护，不自动清理旧文件。

完成标准：重启后仍可判断最近扫描结果；备份恢复可重复验证；升级与回滚边界清楚；异常可在不泄露凭据的情况下排查。

## 阶段四：按实际使用问题扩展

以下按使用反馈选择，避免同时推进：

- 搜索“继续加载”：先确认 Telegram 搜索的游标、跨频道排序、去重和限流契约。当前结果分页只对已返回候选分页。
- Web 编辑常用质量策略：先定义持久化配置与 worker 生效方式，复用后端质量规则。目录、代理与凭据等配置另行评估。
- OpenClaw 联动：先定位实际部署技能与调用配置，再做 API 契约验证及版本同步。
- 任务管理：在真实长期队列需求出现后，再增加更丰富筛选与历史管理；删除历史必须先明确事件和文件保留语义。

完成标准：每项功能有实际场景、明确 API/数据语义及相应验证；不破坏下载可靠性、身份确认和文件安全边界。
