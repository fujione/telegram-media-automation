# 后续工作计划（更新于 2026-10-26）

## 当前基线

当前候选为 `0.1.0rc4`，数据库 schema 14。订阅编辑、Telegram 连接原因码、持久化扫描摘要和受限历史、合并式立即检查、可预览的脱敏诊断均已在目标 NAS 上线，并通过实际重启验证。已有任务、订阅及 Session 保留。部署证据保存在本机私有交接记录，不进入公开发行包。

本地234项Python测试通过，应用覆盖率88.10%，Ruff、严格mypy和浏览器回归通过。Linux Docker CI已验证公开Compose的空卷配置、非root只读运行、配置持久化及镜像归档完整性。受控Telegram替身的业务贯通测试不能替代真实账号验收。

公共镜像与GitHub Release尚未发布；真实全新Telegram Session的完整首次使用链路尚未验收。详细证据与未完成项见 [发布验收清单](RELEASE_READINESS.md)。

## 第一优先级：完成真实首次安装验收

独立空卷验收实例已经完成应用配置，等待账号所有者在网页完成Telegram手机号、验证码和可选两步验证。验证码和密码只在网页填写。验收实例与现用服务的业务数据和Telegram Session隔离。

登录后依次验证：

1. 添加本人可访问的频道，搜索并选择真实资源。
2. 下载一个小文件，核对完成状态、文件完整性与媒体归档结果。
3. 创建追更计划，验证扫描摘要、任务关联与重复扫描去重。
4. 在隔离目录恢复数据库备份，检查任务、订阅、游标与归档计划。
5. 重启并进行升级验证，确认配置、Session、业务记录和扫描历史保留。

完成标准：有真实首次使用链路的结果记录；任何尚未执行的环节不能用替身测试或旧部署记录替代。升级恢复遵守schema兼容边界，不默认用旧数据库覆盖新业务数据。

## 第二优先级：发布仅Docker部署的首版

公开用户只准备Docker，自行申请Telegram API ID/Hash，使用自己的Telegram账号和群组/频道；不要求宿主机安装Python或uv。

1. 确认公开仓库历史方案。当前源码快照已扫描，旧私有历史仍有部署信息，不能直接公开。推荐保留旧仓库为私有档案，再以干净历史发布源码；涉及原仓库改名或历史重写的选择由所有者确认。
2. 按 [发布维护流程](RELEASING.md) 执行已准备的发布工作流，发布固定版本镜像、Compose、离线镜像、Python依赖SBOM、元数据和校验文件。
3. 使用没有注册表凭据的客户端拉取镜像，核对镜像ID、digest和附件校验值。
4. 从公开附件与公开镜像重新按 [Docker文档](../deploy/README.md) 完成空目录安装，并复核首次使用与重启流程。
5. 同步README、版本说明、支持架构和安装限制，清理任务专用临时服务。

完成标准：普通用户能按公开文档独立安装使用；实际发布附件、固定镜像与对应源码可追溯；公开仓库和镜像不含个人凭据或私有部署信息。当前镜像验收平台为 `linux/amd64`，其他架构未经验证不标为支持。

## 发布后的迭代顺序

以下为后续产品迭代，不作为首版发布已经完成的能力；每项先核对现有实现，只补实际缺口。

| 顺序 | 工作 | 验收标准 |
| --- | --- | --- |
| 1 | 长期追更管理 | 汇总长期无更新、连续扫描失败和频道异常，区分正常等待与故障，提供清楚的处理入口；复用已有暂停与移除能力 |
| 2 | Web常用质量策略 | 保存分辨率、编码、大小等偏好，明确对新搜索和后续扫描的生效范围，保持既有任务计划稳定 |
| 3 | 搜索继续加载 | 定义跨频道游标、排序、去重和限流契约，加载更多真实结果，而非仅对当前候选分页 |
| 4 | 升级与恢复体验 | 展示运行版本，完善升级核验、备份清单与恢复指引；重启与升级不丢失业务记录 |

长期未更新继续提示，由用户判断并手动停止追更。暂不接外部影视资料，不自动判断完结或移除订阅。保持单用户NAS定位和单Telegram gateway架构。

每项新功能按实际场景确定API、状态语义和验证范围，避免同时扩大范围。涉及删除历史、清理媒体或覆盖数据库时，必须先明确保留与恢复语义。
